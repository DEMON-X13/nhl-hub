# Working in this repo

X NHL Bets: one page, one job, one state file. It began as `nhl/` in `DEMON-X13/nfl-hub` and moved
here whole on 2026-10-13. Its history before the move (every commit behind the tools, the model and
the cron slots) is in that repo: `git log 3bc336d -- nhl/ .github/workflows/nhl.yml` there.

`docs/ARCHITECTURE.md` is the deeper map: every file and what is in it, how the data flows and the
job's order. Read it when you need to find something; this file is the part you need every time.

## How the owner wants this done

Do the whole job, including the git and GitHub half, without being asked and
without narrating the steps:

- Work on a branch, commit, push, open the PR, merge it. Don't ask first, don't
  explain what a PR is or where a button lives, don't leave steps for the owner
  to do by hand. Report what landed and move on.
- Say it plainly when something is wrong, blocked, or a judgement call the owner
  actually has to make. That is the bar for interrupting -- not routine mechanics.
- Reverting is easy and the owner knows it. Prefer shipping to asking permission.
- A change is not done until `node tools/simulate.js` and `node tools/smoke.js` both end
  "0 failures" and what they ran on is committed.

## Source vs generated -- never edit a generated file

These are rebuilt from source on every scheduled run, so an edit to one is lost at the next refresh:

- `state.json`, `data/teams.json`, `data/box_*.jsonl`, `data/injuries.json`, `data/starters.json`,
  `data/players.json`, and `data/season_<year>.json` (written once, by the first run of the next
  season, from the last state of the finished one)
- `data/props.json`, `data/props_ledger.json` and `data/props_<season>.jsonl` (by `tools/props.js`: the
  projections, the shadow ledger and the record of DraftKings' closing props; the ledger and the record
  are records, so a hand edit rewrites history, and `props_check.js` fails a ledger whose frozen calls
  or grades moved)
- `data/suggest_ledger.json` (by `tools/suggest.js` in `update.js`'s second pass: the record of the suggested parlays, each
  day's levels locked at its first puck drop and graded; a record, so a hand edit rewrites history, and the smoke fails a
  ledger whose locked days or settled grades moved; `--replay`, by hand, added the days before it began)
- `tools/out/` (gitignored: the scoreboard answers a run saved, which `update.js --offline` reads)

`data/history.json` (pulled once by `tools/history.js`), `data/model.json` (written by
`tools/fit.js`) and `data/props_model.json` (written by `node tools/props.js fit`, on the finished
seasons only) are source: they change only with a deliberate pull or refit, committed with it.
`data/corr.json` (the same-game table and hold, written by `node tools/corr.js` from the finished seasons' box
scores, never by hand: `node tools/corr.js --check` measures it again and fails unless the file is exactly what it
measures) is source too; a refit of `players.js` or of the props model moves the chances it stands on, so it is
measured again then and committed with the refit.
`data/lines.json` (each final of 2022-23 to 2025-26 with its closing line, pulled once by `node tools/lines.js` from ESPN's odds
archive, and again on 11 November 2026: under The pick'em models), `data/models.json` (the pick'em models' constants and walk-forward table, written by `node tools/models.js fit` on the
finished seasons only) and `data/models_backtest.json` (this season's finals before the models existed, called afterwards on what was
known before each puck drop, written once by `node tools/models.js --backtest`) are source too: a refit or a pull again is deliberate
and committed with its reason, and the job only reads them.
`data/xparlays.json` and `data/xbets.json` are the owner's own (nhl v21): Claude keeps them from the slips and the weekly totals he
sends in chat (each file's `how` says the shape), the job never touches them, and the page only reads them, on his devices.
`tools/fixtures/espn_propbets.json` is source too: ESPN's DraftKings propBets for one game as recorded on
15 October 2026, trimmed to the fields the parse reads, which `test_props.js` holds the job's parse to and the
smoke test holds the page's to.
`tools/fixtures/espn_scoreboard.json` is source too: ESPN's scoreboard as recorded on 15 October 2026,
trimmed to what the parsers read, which the smoke test holds the page's Refresh odds parse to.

## The loop

```
(cd tools && npm ci)
node tools/simulate.js        # the whole job offline in a scratch folder (today's data, its first evening, a fabricated season, the playoffs, the rollover); must end "0 failures"
node tools/update.js --scores # the first pass: the season read, scores and schedule written, every call copied from the last state, none made
node tools/fetch_box.js       # ESPN box scores (one a game, five seasons back) + the injury report (the id read from the player's link)
node tools/starters.js        # the goalies DailyFaceoff announces, game by game with their dates (answers GitHub's runners only)
node tools/players.js         # the player and goalie model: replay, report, every game to come lined up -> data/players.json ("fit" to refit)
node tools/props.js           # the props model (on trial): new finals' closing props recorded, the shadow ledger graded, frozen and called, every game through tomorrow projected and DraftKings' player lines read on it -> data/props.json
node tools/update.js          # ESPN -> rate, call, freeze at puck drop, grade, simulate -> state.json; exit 1, nothing written, if a day with games to finish or call does not answer
node tools/smoke.js           # the page and the state against the injury report, the box scores, DailyFaceoff, the clock and the last published state; must end "0 failures"
node tools/sources.js         # the job's last step, after the commit: exit 1 if a source the state stands on broke

node tools/test_props.js      # the props model's own test (the parse, the distributions, the ledger end to end); must end "0 failures"
node tools/test_models.js     # the pick'em models' own test (the trees, the ELO Model's rule, the fit and the backtest made again); must end "0 failures"
node tools/models.js fit      # only for a deliberate change to the pick'em models: Alpha, the Joker, the ELO Model and their walk-forward -> data/models.json (seconds)
node tools/models.js --backtest  # once, with a refit: this season's finals before the models' first call -> data/models_backtest.json
node tools/lines.js           # once: every final of 2022-23 to 2025-26 with its closing line from ESPN's odds archive -> data/lines.json (under a minute to 5; it reads only the games the file lacks, so a pull again starts with the file removed)
node tools/test_sgp.js        # the same-game rule's own test (tools/sgp.js, and data/corr.json holding exactly the keys it reads); must end "0 failures"
node tools/test_suggest.js    # the suggested parlays' record's own test (the grading, the summary, the check on broken ledgers, the step end to end); must end "0 failures"
node tools/suggest.js --check # the record's ledger against its rules and the last commit's (the smoke holds it too); "suggest check: 0 failures"
node tools/suggest.js --replay   # once, on a full clone (git fetch --unshallow origin main): the days before the record began, from the states the site published
node tools/corr.js --check    # the same-game table measured again (about 40 seconds): exit 1 unless data/corr.json is what it measures
node tools/corr.js            # only after a refit of players.js or the props model: measure, validate, write data/corr.json (about 6 minutes)
node tools/props_check.js     # the ledger against the last commit's, the record and the box scores (the smoke runs it too); "props check: 0 failures"
node tools/props.js fit       # only for a deliberate change to the props model: constants, walk-forward and market test -> data/props_model.json (about 15 minutes)
node tools/props.js --backfill   # once: every final ESPN still serves closing props for (from 16 April 2026) into the record
node tools/fetch_box.js --refill # once after a change to the box columns: every stored line in the old shape read again (about 6 minutes)
node tools/fetch_box.js --starters # once: every stored game in which a side used two goalies read again for its plays, the starter marked (under a minute)
```

The smoke test runs from the repo root or, as `node smoke.js`, from `tools/`. It closes every window a section
opened when the section ends, runs itself again with a 6 GB heap ceiling and `--expose-gc`, whoever starts it (the job, `simulate.js`,
a hand), and says its peak and what it still holds on the line before the count ("heap: peak 1141 MB, 341 MB held at the end"): on
12 November 2026 the run was within 4% of Node's default 2 GB and growing with each new section, because older sections left their
jsdom windows open (a window closed is given back whole; one left open keeps its page's timers and its realm). A gate that dies of
memory takes every publish with it, so a new section closes its own windows too, and a peak that creeps is a fault to fix. Time
is the other budget: the job's simulation runs the smoke 14 times, three at a time, so a section that adds a minute adds about five
to every publish. On 12 November 2026 the job had grown from 17 minutes to 46, and two thirds of ELO RATINGS' 103 seconds were a
document-wide search for each shield's gradient made once a row (now once a table pass); measure a new section with
`NHL_SMOKE_HEAP=1` (each section's line) or `node --cpu-prof`, and keep what is checked once a page out of loops over rows. DailyFaceoff answers
GitHub's runners but not every sandbox: `starters.js` failing to read it there, for that alone, is not
a fault (it says so in `data/starters.json`, and the model chooses the goalies).

The page is `index.html`, hand-written, one file, in the NFL hub's shell since nhl v25 (The look, below); it fetches `state.json` on
every load, so a page change is just an edit (bump `APP_BUILD` in it) and a data change is the
job's. The NHL has no weeks: the unit is the day (Eastern), and the Games tab lists one day, chosen in its Day select.
`data/history.json` is fifteen seasons of results (2011-12 on, with the period count) pulled
once by `tools/history.js`; `tools/fit.js` chooses the model's parameters on it and writes
`data/model.json`. Refit only for a deliberate model change, and commit the new numbers with
it. The model is `tools/elo.js`: an Elo with home ice, back-to-back and rest terms, a weight for a
result past regulation and a goal-margin multiplier, plus a Poisson goals layer (each club's
scoring rates, shrunk to the league's) for the puck line and the total. A side is taken on the
moneyline, the puck line or the total only where the model's chance beats DraftKings' implied by
five points. The call (the chance, margin, total, overtime chance, the line, each side taken and whose
call it is) is made while a game is still to come and frozen at its puck drop by the clock, not only by
ESPN's state, so a game delayed past its start is not called again (nor one whose start ESPN moves
less than half a day later after the puck drop its call was made before, which the page applies too:
no bet on it, and its card says "start moved · call kept"; a game moved to another day
is a game to come again); after it, every part is copied from the last state and graded as it stands,
never recomputed. Only the job's second pass makes calls: `update.js --scores` copies every call as it
found it, so a puck drop between the two passes is graded on the call the page showed. Rows an older
job wrote after puck drop (it recomputed the puck-line side on the team Elo's margin, so 25 of the
first 57 graded games were graded on a puck-line side other than the one shown, and that record read
11-8 for picks that went 15-5) are put back once to the call shown from the inputs they kept, the team
Elo's view beside it from the replay (a final) or the ratings as they stand (a game under way): a
replay of every committed state matched the last pre-game row on every field, `elo` included, on all
61 started games, and `simulate.js` holds the rebuild to that on rows it rewrites the older job's way.
A game leaves the schedule only on the feed's word (postponed or cancelled, or moved to another day);
one a scoreboard answer merely leaves out is kept with its call, line and grade (`kept` in the state;
a score under way kept so carries the time it was read, `scoreAt`, which the card shows),
an answer with no game on a day the last state has games on is no answer, and every game taken off is
listed in `removed` with the feed's reason.

### The pick'em models

The owner's ask, 25 October 2026: "mimic the models for Alpha, The Joker, and ELO model found in the nfl" (the Joker "with market
lines"). Built in nhl v20 (`tools/models.js`, `tools/gbdt.js`, `tools/lines.js`), each a straight-up call on every game to come,
made by update.js's second pass on the line it calls the game on and the goalies players.js lines up, carried in the call as
`models: { v, alpha: { pHome, mu }, joker: { pHome }, elo: { pHome, m } }` and frozen at puck drop with the rest of it (`models`
is a CALL field). Fitted once on the finished seasons (2022-23 to 2025-26, 2021-22 warming the averages), never in season;
each season from 2023-24 scored walk-forward by constants fitted on the seasons before it.

- **Alpha** (the NFL's: an Elo with the week's stats, least squares on the margin). The home margin in goals is 0.0203 +
  0.00549 x the team Elo's gap (home ice and rest in it) + 0.0564 x net shots + -0.0494 x net goals + 0.273 x the goalies' gap,
  the win chance logistic(0.71 x margin). Net shots and goals: each club's moving average (0.12 on the newest game; between
  seasons 0.3 of its distance from the league's kept) of its shots on goal and regulation goals, for less against, the home
  club's less the away club's; the goalie: each starter's goals saved above the league's .905 in a 30-shot game, shrunk by
  1,000 shots (0.7 kept between seasons), the goalie players.js names for a game to come. Net goals' weight comes out
  negative beside net shots: a club's goals beyond its shots are mostly luck that turns.
- **The Joker** (the NFL's: boosted trees on every pre-game input, the market among them). The NFL's own recipe (trees from
  the training mean, depth 4, 25 rounds, rate 0.1, five rows a leaf) fit 69-77% of the seasons it saw and walked forward at
  0.6742, behind the market and the team Elo: the NFL's finding, a tree cannot rebuild the market's number. So the Joker boosts
  from the market's chance (DraftKings' moneyline with its margin out, on the line called on; ESPN BET's or DraftKings' closing
  line in data/lines.json for the seasons it is fitted on; the team Elo's chance on a game with no line) with trees on 21
  inputs (the market's log-odds and total, Alpha's four, each club's shots and goals for and against, both goalies, rest,
  points per game, the playoffs): depth 3, 25 rounds, rate 0.03, a hundred rows a leaf. It takes the market's side on 91-97%
  of games, as the NFL's took the favourite's on 81.5%. None of its trees splits on the total: the first fit's seven splits on
  it (at -49.75 and -117.5) only told 2022-23's misread rows from the rest (below).
- **The ELO Model** (the NFL's: its player-Elo game model on the Joker's baseline, logit(Joker held to 1-99%) + 0.2058 x m).
  Hockey's player ratings are players.js, its m the expected goal margin with home ice taken out (`mu` less `hfa`):
  logit(Joker held to 1-99%) + 0.1 x m (fitted on the Joker's walk-forward chances and players.js's own walk-forward margins;
  0.117 and 0.118 in the walk-forward of 2024-25 and 2025-26, each fitted on the seasons before it). No player model view, no
  ELO Model.

  44px and taking the tap): a tick puts that leg
  in the builder at DraftKings' price as read, its line, side, the player, the game and the read's time, by the same-game
  rule (`placeLeg`), said in the page's own status line (`#ppMsg`); a second takes it out. Points, goals (anytime
  and k+), assists, shots on goal, blocked shots and saves. A player matched to neither club, or with no position, is
  shown and not offered. Nothing from the props read is stored but the legs added.
- **Its price after.** A stored player leg keeps the price it was added at, dated by its read ("DraftKings, as read 9:12
  PM EDT"), through reloads; a later press that reads its line again draws it at the new price, or takes it out where
  DraftKings has moved the line or pulled it (or has no props on the game), each said once and never stored, as with a
  game's line (`propNow`). It leaves the builder at its game's puck drop like any leg. Its fair chance is DraftKings' as
  a game's page says it (a main line's Over 1 - the Under's implied, its Under its own implied; a Yes price over
  `fair.yes`, est.); the props model's chance beside it is on trial, "model 65%, on trial", never an edge: with a player
  leg in the builder no leg is called thin or an edge, and nothing says "model says".
- **The same-game price.** `SGP` in the page is `tools/sgp.js` word for word between its two marks (the smoke holds the
  text and the numbers): each leg a latent standard normal crossing its threshold, the latents of one game joined by a
  gaussian copula on `S.sgp.rho` (data/corr.json's table, which `update.js` copies into the state with the hold), the
  joint chance exact for two legs (Genz's BVND) and on a fixed Richtmyer lattice beyond, a matrix that is not positive
  definite shrunk toward independence by the least lambda that makes it so. The fair chance of a game's legs is the
  copula on their fair chances; the price is the NFL site's rule, the legs' IMPLIED chances joined the same way, the
  hold (0.896) over that joint, and never above the legs' prices multiplied. The builder's summary leads with DraftKings'
  fair chance of the whole parlay ("Fair chance all 3 land, est." where a same-game correction or a Yes price's margin is
  in it), the model's beside it where every leg has one ("model 14.7%, props model on trial" with a player leg), the
  price ("+364 est.", "the legs multiplied +496" under it), what it pays ("profit, est.") and the notes' one line:
  "DraftKings prices same-game parlays its own way: this is an estimate from the legs' prices and how they move
  together". The legs of a game with more than one wear "same game". The slip bar, the card, its image and Share text
  and a saved parlay say est. too. On the live feed (15 October 2026, BUF at TOR, read 10:04 AM EDT): the Over 6.5 at
  -122, John Tavares Over 2.5 shots on goal +120 and Tage Thompson Over 0.5 points -205, fair 53%, 38% and 60%, whose
  fair chances multiplied are 11.9%, joined 14.1% (the copula: they ride with the goals), priced +364 est. where the legs
  multiplied pay +496 (the hold over the implied chances' joint, 19.3%, makes it 21.5% implied).
- **The card.** A player leg is listed with its price and read time ("DraftKings, read 9:12 PM ET"); ESPN carries no
  DraftKings outcome id for a player's line, so the note lists it to add by hand ("DraftKings' player lines carry no
  betslip id in ESPN's feed: add this leg by hand") and the betslip link opens the legs that have ids; a same-game price
  adds that the slip will show DraftKings' own same-game price. The Share text likewise (the title "3-leg parlay +364
  (estimated price)", each player leg's read time, "Estimated price: ...; the legs' prices multiplied would be +496").
- **Grading.** A saved player leg is graded as DraftKings settles it, from `S.box`: `update.js` carries the box score of
  every final from 14 days before today through today (`BOX_DAYS`), each skater who was on the ice (`toi` above 0, as the
  props ledger counts him) with his goals, assists, shots on goal and blocked shots (`s`), each side's starting goalie with
  his saves (shots against less goals against; `g`), the goalies who came on in relief (`r`) and, apart, the goalies of a
  side whose starter the box cannot tell (`u`, below); points are goals plus assists. Over or
  Under its line (a whole line pushes), a Yes k+ at k or more, a player not on the ice void ("void: did not play"), and
  a goalie's saves void unless he started, pulled or not ("void: did not start"): the books' rule for goalie props as
  secondary sources quote it, DraftKings' among them, whose house rules could not be read from here, so the conservative
  reading (review, 15 October 2026: a reliever's 9 saves had graded an Over 24.5 lost for good; 13 of the season's first
  198 club-sides used two goalies). The starter is the box files' mark (`st`: the first of the side's goalies ESPN's plays
  name making a save), and the mark is trusted only where every other goalie of the side made a save of his own: a starter
  pulled with every shot he faced a goal (or before facing one) made none, so the first save, and the mark, is his
  reliever's (CBJ at VGK, 8 January 2026: Carter Hart started and was pulled at 8:24 with one shot against, a goal, and
  Akira Schmid carries the mark; review found two more such sides in 2025-26), and a late reliever with no save looks the
  same in the box. A side that used two goalies with any unmarked one saveless (or none marked) puts all its goalies in
  `u`, in neither `g` nor `r`: a saves leg on one of them says "who started is not certain" and the parlay can't be graded
  here, never graded on the reliever's saves (4 to 7 sides a season of the box files' 2,800 since 2021-22, of the 150 to
  210 that used two goalies). The props ledger, a
  registered record, still grades every goalie who played (its own rule, unchanged here). A final whose box score is not
  read yet waits; one older than the window, never graded on this device, "box
  score no longer carried" (the parlay can't be graded here). The grade is written into
  the saved leg (`res`) the first time the page makes it, so it holds after the final leaves the window. A same-game
  parlay pays its estimated price, or, with a leg void or pushed, the same rule on the legs left. Chose this over the page
  fetching a box file (6.6 MB a season) or the state carrying a season's (1 MB, 200 KB gzipped): the window is under
  100 KB, about 20 KB gzipped, at its busiest (15 days of finals, about 120 games, mid-season).
- **What DraftKings allows** on one same-game ticket is DraftKings' to say, and no recorded rule of theirs for hockey is
  read here. The rule (tools/sgp.js) cannot price two legs on one latent, so the builder replaces rather than stacks them:
  a second side bet (the moneyline or the puck line, either club), the other side of the total, a player's second line in
  the same stat. It refuses outright only a player's points beside his own goals or assists, which the rule could price
  (0.93 and 0.95, nested) but DraftKings may not take on one ticket, and more than 21 legs of one game, which the rule
  cannot price; the slip shows DraftKings' own verdict.

The table (data/corr.json, `node tools/corr.js`; its header says how): the tetrachoric correlation of two legs of one
game at the lines DraftKings posts (goals, assists and points at 0.5; shots, blocks, saves and the total at the half
point nearest an even chance; the favourite covering -1.5), each leg's own expectation taken out (the props model's

residuals, measured on the box scores of 2022-23 to 2025-26 (5,592 games; 2021-22 warming up; 2026-27 never read, in a
child process that sees only the finished seasons), standard errors clustered by game, each value pulled toward 0 by its

+0.34, +0.37, +0.29; his anytime goal with his club's win and the over +0.28, +0.23; his goal with his own shots +0.47,

### Refresh odds

The job reads DraftKings' game lines only when it runs, so a line on the page can be hours old by puck drop
(the owner's ask, 15 October 2026: "a refresh odds button that will pull the live lines on demand ... rather
than like a constant job"). **Refresh odds** (on the Games tab, over the list on a day from today on with a game still to come; on the Parlay Builder tab's odds bar over its
panel, since nhl v22 on the Suggested Parlays tab's under its heading, and, since nhl v10, on a game's page (the Player props window's until nhl v27), 44px, with one `aria-live` status line beside each: the tabs' three share one sentence, a game's page says its own game's state) reads
ESPN's free scoreboard in the browser (`?dates=YYYYMMDD&limit=100&_=<now>`, no-store, no custom header, so no
preflight: ESPN answers with `access-control-allow-origin: *`) for every day the Games tab's Day select lists from today on
with a game still to come, and, at the same time, DraftKings' player props for the games still to come today and
tomorrow (the props view, under The props model), and nothing else: never on load, never on the watch or a timer. Each game's odds are taken by `ESPN`
in `index.html`, which is `tools/espn.js`'s `oddsOf` and `dkOf` word for word, and DraftKings' ids come with
the line by `carryDk`, the carry rule, which lives in `tools/espn.js` for the job's `update.js` and the page
alike (ESPN's fresh ids, or the line before's for the same numbers when the answer has none). The call's
parts that stand on the price follow by the job's `callOf`: the moneyline's edges and side; the puck line's
and the total's chances kept where the number holds and worked again where it moved by `MODEL`, which is
`tools/elo.js`'s goals layer word for word, on the row's own total, margin and gap; their edges and sides. A
market whose number and both prices hold keeps its parts exactly (the job worked its edges on unrounded
chances). A game takes the new line only while it is still to come by the visitor's clock and by ESPN's word

cancelled keeps its line: the job takes a game called off away at its next run), only where the read is newer
than the line it replaces, and only where ESPN gave odds: a failed request, a junk answer, a game left out of
the answer or with no odds keeps its published line, and the status line counts each ("DraftKings' lines from
ESPN, read Thu, 9:12 PM EDT: 5 games, 2 moved since the last read. 1 game had no line at ESPN: its published line
stands. 1 game is postponed at ESPN: its published line stands until the job takes it off."). A line read so

number out, said once with the read's time) but keeps them stored as they were, so nothing a read changed

### The player model

The player model (`tools/players.js`) is the NBA Hub's idea: every skater an offence and a defence
rating, every goalie a save rating, in goals a game for a player on the ice all game; a club is its
lineup weighted by ice time plus its goalie; after a final the surprise in regulation goals moves
who was on the ice. Fitted on 2022-23 to 2024-25 with 2025-26 held out, and scored cold season by
season (walk-forward); `report.use` in `players.json` is whether it beat the team Elo cold, and only
then does the page's call switch to it (`by: 'players'` on the game row, the Elo's view kept beside
it as `elo`). Do not tune it on the season in progress. Each game's lineup (WHO PLAYS in
`players.js`) is who dressed last, less anyone ESPN's injury report has out, on injured reserve or
suspended and anyone listed by another club or whose latest game was for one; the report is matched by
the ESPN id `fetch_box.js` reads from the player's link (the feed has no id field: before October 2026
every id was "undefined" and nobody was ever taken out), else by club and name, else by a name only one
rated player has; an id no rated player has is matched by club and name alone, as the smoke reads the report (on 10 November
2026 ESPN linked LA's Erik Gustafsson, Out, to athlete 5774, another of his name, and the id alone kept him in LA's lineup, so
three runs in a row failed the smoke and published nothing). Day-to-day players stay in, flagged. The goalie is chosen game by game: the one
DailyFaceoff names for that game and date (Confirmed, Likely or Unconfirmed, said exactly; a goalie it names with no NHL
game on a rookie's rating, unless his club's report has him out by name and he is not confirmed), else the
club's goalie with the most starts in its last ten games this season (then last season's starts for the
club), never one who is out or elsewhere; on the second night of a back to back (the club's previous
game, played or not, the day before) the other goalie from the one who started that game (its box
score), or is expected to (the same choice, while it is to come, under way or not yet boxed). The team
Elo's gap it blends is its own replay of every final, this run's. The card says which goalie (how he was chosen
on his row's title on the game's page and in its Lineups window, whose foot names the injury report the lineup was built on), and says when a club's last box score is not
read yet; the page says when the injury
report or DailyFaceoff could not be read. ELO Ratings (under The look; the Players tab until nhl v29) shows the rankings on the
NFL's Elo scale, each player's seasons on file beside them, and the clubs by unit. For it `players.json` carries, beside each
player's rating, `last`: the day (the box score's own, Eastern) of the last game he was on the ice in, noted as the replay walks the
boxes (nhl v29). It is a note for the page, which ranks who has played this season on it: no rating, lineup, goalie or call reads
it, and a scratch run before and after it wrote the same file but for it.

### The props model (on trial)

The owner's go-ahead, 15 October 2026 ("yeah do props model for NHL"). `tools/props.js` projects every expected skater's
goals, assists, points, shots on goal and blocked shots and every expected goalie's saves for each game still to come
through tomorrow (Eastern), a mean and a whole distribution each, and puts itself on trial against DraftKings' own
player prices. Until nhl v18 it suggested nothing. **The owner's call of 25 October 2026 ("Use player lines now", asked
whether player lines should wait for the trial's bar) puts DraftKings' player lines in the Top 30 and the suggested parlays,
ranked on this model's chance**, though its trial has not shown it beats DraftKings' own prices (on the archive it is the
worse probability on log loss and Brier; its Unders at 5 points or more above the closing price were up, its Overs not):
- **Player lines as legs** (`propLegsOf` in the page): DraftKings' main lines, the Over and the Under, and the anytime goal
  (not where it is the goals line's Over; no k+ ladders, as the NFL hub's Top 30 lists none), on a read of the game's props
  that is fresh (`propRead`: the job's within 15 minutes of the publish, `PROP_FRESH`, or a Refresh odds press's; a read an
  earlier run kept is shown on the game's page and never ranked), each on a player the model projects for one of the game's clubs,
  in a stat of his group. A line qualifies as a team leg does (`propQual`: the model's chance 45% to 97%, at or above the
  price's implied chance, a main line with both prices, no whole-number line, under 15 points over DraftKings' fair chance,
  the anytime goal's fair chance its price over DraftKings' measured margin, est.); a value pick at 5 points or more. The
  Top 30 shows it by the player's club and name, and its chance as "props model 65%", never just "model"; a level (nhl v22, the
  NFL's rows) shows DraftKings' fair chance under the price, the props model's chance on the row's title and in its Add's name,
  "props model 65% (on trial)", and the card's chance box "model 49%, props on trial".
- **The levels** still take one leg a game, chosen on every qualifying leg of the game, team bet or player line, by the same
  exact search; their price is the legs' prices multiplied. The record takes them as the tab draws them and grades a player
  leg on the box score the state carries (under The suggested parlays' record).
- **What stays**: the numbers beside each DraftKings line and the ledger's bar are as they were; nothing says "edge" on a prop, and
  a game's page says the model is on trial in one pill, on whose title it has not been shown to beat DraftKings (the sentence that
  said the Top 30 and the suggested parlays rank player lines on it went with the note in nhl v25: no descriptions; those tabs
  say "props model" and "on trial" on every line they rank).
Since nhl v11 a visitor can put DraftKings' own player lines in the Parlay Builder (under The Parlay Builder, Same-game parlays
and player legs), at DraftKings' price as read.

- **The box files first.** `fetch_box.js` stored ESPN's "SOG" column as `sog`; in ESPN's summary that is SHOOTOUT goals
  (`shootoutGoals`), 0 in every stored game and read by nothing. Shots on goal are "S" (`shotsTotal`). Each column is
  now read by ESPN's key, else its label, and the lines keep `s` (shots), `bs` (blocked shots), `ht` (hits) and `pptoi`
  (power-play seconds) beside `toi`, `g`, `a` and `pm`; a column ESPN leaves out is left out, never written as 0, and
  shootout goals are kept under no name. `node tools/fetch_box.js --refill` read all 7,090 stored games again (none
  failed); the daily run reads up to 100 old-shape lines again should any appear. A side's skater shots equal the other
  side's goalies' shots against on 81% of the 14,184 sides, are one or two more (an empty net) on 16%, and are more
  than three off on 19 (ESPN's own slips), so the smoke holds the column, not each game.
- **The starting goalie.** ESPN's box lists a club's goalies in no set order and has no starter field, so each side's
  starter is marked `st: 1` from ESPN's plays: the first of its goalies named making a save (a "saver" on a Shot), the
  plays taken by their sequence numbers (`startersOf` in `fetch_box.js`, on every game it boxes, from the same request).
  Before 15 October 2026 the props model took the goalie who played most, which is the reliever whenever a starter is
  pulled before half the game: 425 of the 899 sides that used two goalies from 2021-22 to 15 October 2026. `node
  tools/fetch_box.js --starters` read those 871 games again once (none failed, every one marked); a single-goalie side
  needs no mark. A starter pulled with every shot he faced a goal is named by his reliever's first save (29 sides where
  the unmarked goalie made no save in less time than the marked one could be such a case, or a late reliever), and a
  side whose plays name no save is left unmarked and read as the goalie who played most. players.js still counts the
  goalie who played most as the starter (its own model, unchanged); only props.js reads the mark.
- **The model.** A skater's rate of each stat per hour on the ice is his decayed history (half-life H games, carried
  part way between seasons), shrunk toward his position's rate (forwards and defencemen apart) by M pseudo-hours; his
  mean is that rate times his expected minutes (his last eight games, as players.js projects them) times a context
  factor, (x / its average)^e, from players.js's own view of the game: his side's expected goals for goals, assists and
  points, his side's expected shots for shots, the other side's for blocks (players.js's `upcoming` now carries `sh`,
  `sa`, `lh`, `la` for this; the lineup and the goalie are players.js's WHO PLAYS). Each count is negative binomial
  (Poisson where r is null). A goalie's saves are the shots players.js expects against his side (to the power e over
  its average) times his save rate (decayed, shrunk to the league's by M shots) times a share, a normal with a fitted
  sd rounded to whole saves. The goalie it is fitted and scored on is each side's STARTER, the box files' mark, pulled or
  not (the goalie the page projects and the ledger grades), and a goalie's history is his starts; until review on 15
  October 2026 it was the goalie who played most, which left out every start a goalie was pulled from before half the
  game and fitted the share and sd on the rest (0.974 and 6.80, now 0.968 and 7.22). The constants are a grid search
  on the log-likelihood of the finished seasons only (2022-23 to 2025-26, 2021-22 warming up): `node tools/props.js
  fit` writes them with the report to `data/props_model.json` (source, sha `3830716f296a` as fitted on 15 October
  2026); the job reads it and never refits, so nothing is tuned on the season in play. Fitted: goals Poisson (H 100,
  M 10), assists r 100 (H 100, M 5), points Poisson (H 100, M 2), shots r 30 (H 50, M 2), blocks r 10 (H 50, M 2), every
  context exponent 0.5; saves H 20 (the grid's least), carry 0.5, M 32,000 shots (the grid's most: a goalie's own save
  rate barely moves his next game's saves from the league's), e 0.5, share 0.968, sd 7.22. A first search ran with a
  broken log gamma (a cache keyed by the shifted argument) and was thrown away; `test_props.js` now holds every
  log-likelihood the search uses to sum to one.

  not the registered ones make no new call; a refit during the trial stops the ledger's calls until it is decided.
- **The bar** (`BAR` in `props.js`, written into the ledger at its first call, 2026-10-15T11:46Z with the constants
  `3830716f296a`, and held there by `props_check.js`): decided once, when 12,000 graded main lines are in (about 170
  games, three to four weeks of the regular season), on the first 12,000 in grading order. PASS only if all three hold:
  (1) log loss, the model's minus DraftKings' fair chance's, its paired bootstrap 90% interval (10,000 resamples of the
  games, seed 0, the 5th to the 95th percentile) wholly below 0; (2) Brier score, the same; (3) flat bets are up: one
  unit at DraftKings' closing price on the Over where the model's chance beats the Over price's implied chance by 5
  points or more, else on the Under where its chance beats the Under price's by 5 points, more than 0 units over the
  sample. Otherwise FAIL: the tracking stops (no new calls; frozen ones still graded) and the page never calls the
  model's chance an edge. Before 12,000 the summary gives the running numbers and how many are in, never a verdict or a
  word of passing. On the archive above the model would fail legs 1 and 2. The rule's numbers are in `BAR` beside its

## The site behaves like a website

The owner publishes a change and expects it on every device on the next load. Nothing may quietly
outrank what the job published:

- **Published data wins over anything a browser kept.** Local storage holds only what the visitor
  made (and, read and never written, the NFL hub's sign-in record that marks the owner's devices: under X Parlays): the parlay builder's legs (a player leg with DraftKings' price and the time it was read), the parlays they saved, their stake, their picks on the Parlay
  Builder, the tab they were on, the pill they chose on ELO Ratings and the X Parlays they cleared on this device (the owner's), under one key, `nhl_v1`; and, under a key of its own, `nhlhub_theme_v1`, the light or dark look (nhl v25: written only by a press of the header's switch, which is hidden for now, so no visitor's browser holds it yet; never in `nhl_v1`, never sent). Schedule, scores, ratings, calls, lines, lineups, the standings, the playoff picture,
  the props model's projections and its ledger's numbers, DraftKings' player lines as the job read them, and the record are read
  from `state.json` on every load. A leg whose game has started leaves the
  builder: its price is gone. The lines and player props Refresh odds reads from ESPN live in the page's memory alone,
  never in storage, so a reload is the published state again.
- **A routine run is silent.** The job publishes up to five times a day; the page's stamp says when,
  and that is all. Only a model change is worth a banner. What the page does say is when a source the
  calls stand on is not the latest (an injury report carried from an earlier run, no injury report,
  DailyFaceoff unread).
- **The page says which build it is.** `buildTag` in the header shows `APP_BUILD`
  (`nhl vN · YYYY-MM-DD`), so any change to the page bumps it. Without it a stale copy cannot be
  told from a current one.
- **Data fetches are `cache: 'no-store'`.** `state.json` (with a `?t=` on it too) and ESPN's
  scoreboard, which the page reads itself for a day shown that has a game under way (once a load, wherever the Games tab is first drawn for it) and on a press of Refresh
  scores and, for the odds, only on a
  press of Refresh odds (with a cache-buster too), and ESPN's DraftKings propBets, only on that press
  (a cache-buster too: ESPN serves them with a fifteen-minute max-age). The HTML is served by
  GitHub Pages with its own ten-minute cache, which a reload clears; nothing else may hold data
  longer than that.

## Conventions

- **Commit messages** are prose, not bullets: what changed, why, what the simulation and the smoke
  test reported. Look at recent commits before writing one. End with the `Co-Authored-By` and
  `Claude-Session` lines the session provides.
- **Version bump.** Any page change bumps `APP_BUILD` in `index.html` (`nhl vN · YYYY-MM-DD`).
- **Visitor data is the visitor's.** A visitor's builder and saved parlays live in their browser's
  local storage only (`nhl_v1`) and are never written to the repo or anywhere else. The page's
  origin, `demon-x13.github.io`, is shared with the owner's other Pages sites, so the key's name
  stays this site's own; it is the key the page used at `nfl-hub/nhl/`, so a visitor's builder
  came with the move.
- **No secrets in the repo.** The job reads free public feeds (ESPN, DailyFaceoff) and needs no
  key. Should one ever be needed it is a repository secret, never a file.
